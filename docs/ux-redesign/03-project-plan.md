# 03 · 项目规划（电脑 · 平板 · 手机）

日期：2026-10-19。依据：已验收基线 `bbcda69`、v4 设计（`34b8ee5`）、`ux/v4-device-first` 上已完成的 v4 前端实现（`df91601`，未审核）、docs/PRODUCT.md 与 docs/ROADMAP.md。

## 1. 产品预期

- 电脑是工作台：AI 工具在电脑上运行，项目、会话、配置都在这里。
- 平板是阅读和审阅的屏幕；手机是随身遥控器。两者是原生应用，登录同一账号来查看和控制你的电脑，自己不运行 AI 工具，也不出现在“设备”列表里。
- 结构始终是 账号 › 设备 › 项目 › 会话。一个项目就是一台设备上的一个文件夹。

| 功能 | 电脑 | 平板 | 手机 |
|---|---|---|---|
| 待处理（批准 / 完成 / 失败） | ✓ | ✓ | ✓ 首页 |
| 批准 / 拒绝、回复、停止 | ✓ | ✓ | ✓（回复为简短输入） |
| 浏览 设备 › 项目 › 会话 | ✓ | ✓ | 只看最近和运行中的 |
| 完整对话 / 变更 | ✓ 逐行 | ✓ 逐行 | 只看对话；变更只看摘要 |
| 新建会话 | ✓ | ✓ 已有项目 | — |
| 项目内搜索 | ✓ | ✓ | — |
| 添加项目、导入以前的会话、添加设备 / 配对 | ✓ | — | — |
| 设置 / 诊断 / 首次启动 | ✓ | — | 只有通知开关 |
| 通知 | 系统通知（已有） | 推送 | 推送 |

## 3. 分工

每个阶段都走同一个流程：

1. 我做设计：原型、截图、交接文档，后端阶段写接口和数据说明。
2. 你确认设计。
3. 我写给编码智能体的提示词。
4. 编码智能体在单独的分支和工作区里实现，按步骤提交，不推送、不部署。
5. 我审核：读 diff，跑 typecheck / lint / test / build，对照设计和本文 §6 的不变量，写审核报告；有问题就写修复提示词，再审一轮。
6. 你在真机上验收，然后合并、发布。

只有你能做的：部署 Control Plane 和 Relay，Apple 开发者账号和 Google Play 账号，签名证书，真机测试，商店上架，替换已安装的版本。

## 5. 原生应用的技术方案（M0 前需要你定）

难点不在界面，而在连接：手机必须实现和电脑一样的 Supervisor 客户端（TLS 1.3、Host 固定、绑定 TLS 导出密钥的设备证明、Relay 帧协议）。现在这个客户端是 Node 的 TypeScript，手机上不能直接用。

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A（推荐）** | SwiftUI（iPhone / iPad）+ Jetpack Compose（Android），共享一个 Rust 核心（rustls + Supervisor / Relay 协议，UniFFI 生成 Swift 和 Kotlin 接口） | 界面最原生；安全协议只实现一次；Rust 和现有 Tauri 同一语言 | 两套界面代码 |
| B | Tauri 2 移动端，复用现有 React 界面 + Rust 核心 | 代码最少 | 体验接近网页，和“原生应用”的目标不一致 |
| C | 只做 iOS / iPadOS，Swift 实现客户端 | 最快出第一版 | Android 以后要重写一遍协议 |

另外需要你定：先做 iOS 还是两个平台同时做；Android 平板要不要支持。

## 6. 每个阶段都要守住的不变量（审核清单）

- 账号、ProductDevice、Host、Relay、Machine 的身份和信任彼此独立，一种不能换成另一种。
- 手机和平板只通过 Supervisor 访问电脑，不直接连本机 4317 端口。
- control 权限必须由电脑上的用户逐台批准，并且可以撤销；read 和 control 分开。
- 远程操作沿用本机门控：`actionId` 幂等，运行中不能归档，失败后不自动重发，忙碌时返回 409，审批和停止只对支持的 AI 工具开放。
- 推送和系统通知都不含会话标题、提示词、命令和路径。
- 界面只显示后端真实提供的能力；还没做的只出现在后续规划。
- 不读写 `.secrets/` 和凭据文件；编码智能体不部署、不替换已安装的版本。
