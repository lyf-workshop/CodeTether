## 七项结论

1. 已测受保护目录的属性调用可以成功，不能据此证明之后的 readdir 有权限；先前一次拒绝状态下 Host access 返回 EPERM。
2. 本轮 Host 和 Node 的 readdir 在用户处理弹窗前等待，处理后返回；最长等待 84,969 ms，未测试无限等待。
3. 两进程被拒绝后再次读取均快速返回 EPERM，没有报告再次弹窗；重读并非紧接点击。
4. Host 文稿允许在同一签名重启后保留；重建后 CDHash 改变并再次出现授权弹窗。
5. 一个挂起读取时 stat 和 DNS 快速完成；四个挂起读取时两者超过三秒，读取返回后才完成。
6. launchd Node 的受保护文件夹读取会弹窗，显示名称为 codetether-node；文件与文件夹页面提供开关。
7. Node 同一路径重启后文稿允许保留；同路径 CDHash 变化后及相同二进制复制到新路径后均再次弹窗。

## 限制与收尾

- 弹窗名称、选择由用户确认；未截得仅包含授权窗口的截图，未记录弹窗精确出现时刻。
- 曾观察到旧轮次长时间挂起：Host 四读取约 5,713,500 ms 后成功；重置后另一 Host 读取约 348,535 ms 后 EPERM；Node 读取约 918,228 ms 后 EPERM。这些旧轮次没有连续画面，无法断言整个等待期间是否存在弹窗。
- 实测后停止测试标签 r4、r5、r6、r7，删除其 plist、程序和数据；取消两个 launchctl 环境变量，重新对 Host Bundle ID 重置桌面、文稿、下载授权。正式 `com.codetether.node` 仍 running，PID 876。
- 用户随后确认，补充截图尝试的 r6 实例也显示“codetether-node”文稿授权弹窗并选择允许；该实例已在回复到达前停止，未保留返回时间。
- Windows 设备页由用户确认该 Mac 在线且可连接。安装版 `/Applications/CodeTether.app` 签名校验通过，但重新启动后约 0.45 秒退出；系统日志不足以确定原因，桌面应用未能恢复运行。
- 根据用户要求，桌面、文稿、下载的三个 `b4-probe` 测试文件夹已通过访达移入废纸篓。系统设置仍显示多个同名 `codetether-node` 条目；由于无法确认各条目对应的路径，未移除，以免误删正式 Node 的授权。用户报告未找到 `codetether-node` 条目；上面的列表为实测时通过系统设置观察到的状态。
